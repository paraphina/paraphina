# Telemetry Schema v2

Telemetry schema v2 is the Phase 5.1 non-live EV/replay/shadow telemetry
contract. It is additive to v1 and does not change existing v1 producers.

The validator selects the schema for `telemetry.jsonl` from the first record's
`schema_version`:

- `schema_version: 1` -> `schemas/telemetry_schema_v1.json`
- `schema_version: 2` -> `schemas/telemetry_schema_v2.json`

Mixed-version files are invalid. Unknown schema versions are invalid.

## Required Envelope

Every v2 event requires:

- `schema_version`
- `event_type`
- `event_seq`
- `timestamp_local_ns`
- `run_id`
- `baseline_commit`
- `no_live_flag`
- `approved_for_live`
- `approved_for_canary`
- `approved_for_capital_escalation`
- `live_orders_allowed`
- `capital_change_allowed`
- `risk_limit_relaxation_allowed`

`event_seq` must be monotonically increasing.

For Phase 5.1 non-live evidence these safety fields must remain false. This
prevents a replay/shadow artifact from being mistaken for live, canary, capital,
or risk-limit authorization. The schema validator enforces these exact values
for v2 records.

## Event Families

The v2 contract recognizes the Phase 5.1 event families approved by the EV
revision addenda:

- `V2_RUN_CONTEXT`
- `V2_MARKET_SNAPSHOT`
- `V2_PAIR_EDGE_SNAPSHOT`
- `V2_EV_EVALUATED`
- `V2_ORDER_INTENT`
- `V2_ORDER_LIFECYCLE`
- `V2_FILL_OBSERVED`
- `V2_FAST_HEDGE_DECISION`
- `V2_HEDGE_LIFECYCLE`
- `V2_INVENTORY_SNAPSHOT`
- `V2_BALANCE_SNAPSHOT`
- `V2_REPLAY_LABEL`
- `V2_GUARDRAIL_EVENT`
- `V2_LIGHTER_ACCOUNT_PROFILE`
- `V2_LIGHTER_ACCOUNT_LIMITS`
- `V2_LIGHTER_OFFICIAL_LIMITS_DOC`
- `V2_LIGHTER_ACTIVE_ORDERS`
- `V2_LIGHTER_TRADE_ATTRIBUTION_SAMPLE`
- `V2_VENUE_NATIVE_ROLE_SAMPLE`
- `V2_VENUE_NATIVE_LIMIT_PRESSURE`

The Phase 5.1 shadow harness currently emits source-linked
`V2_EV_EVALUATED` and `V2_REPLAY_LABEL` records. These records include
`source_t`, `source_line`, `source_record_sha256`, `model_features_hash`,
`calibration_bucket_id`, `calibration_status`, `decision_reason_secondary_list`,
and `binding_constraints` so candidates can be traced back to the v1 telemetry
line that produced them and reviewed against explicit calibration gaps.

All Phase 5.1 shadow candidates remain `HOLD` until calibration evidence exists.
`V2_REPLAY_LABEL` records are counterfactual decision labels, not realized fills
or economic proof.

The current HOLD taxonomy includes missing P-fill, markout, hedge-success,
queue-reset, churn, and tail-risk calibration, plus sparse bucket and
counterfactual-only labels. These are review blockers for admission, not
runtime order controls.

Phase 5.1b adds read-only Lighter account/native-limit event families:

- `V2_LIGHTER_ACCOUNT_PROFILE` records the account/profile evidence boundary,
  a nonsecret account hash, account type if observed, market metadata, fee raw
  fields, and fee/decimal metadata when available.
- `V2_LIGHTER_ACCOUNT_LIMITS` records authenticated native limit snapshots such
  as sendTx, REST/weighted request, pending-order, active-order, and volume
  quota fields where the endpoint exposes them. It also records observed Lighter
  user-tier and fee-tick fields when the account limits payload exposes them.
- `V2_LIGHTER_OFFICIAL_LIMITS_DOC` records the official-doc limit-cap snapshot
  used by Phase 5.1m. These caps can support current active-order capacity
  context only when paired with observed active-order counts; they must not be
  treated as label-event-time native-limit pressure, sendTx remaining pressure,
  or REST remaining pressure unless explicit event-time alignment is present.
- `V2_LIGHTER_ACTIVE_ORDERS` records active/pending order counts and native
  headroom against observed account-limit fields or official-doc active-order
  caps, with conflicts preserved as HOLD evidence instead of inferred headroom.
- `V2_LIGHTER_TRADE_ATTRIBUTION_SAMPLE` records read-only maker/taker trade-role
  sample counts for attribution calibration, including Lighter trade-shape
  inference from account side plus `is_maker_ask` when explicit role labels are
  absent. It is not balance-authoritative PnL.

These records are generated by
`tools/phase51b_lighter_account_limits.py` from captured JSON files or explicit
read-only HTTP GETs. They remain `HOLD`, non-live, nonfinancial evidence and do
not relax EV admission, canary, capital, or live-order blocks.

Phase 5.1n adds derived, repo-owned non-live evidence labels:

- `PHASE51N_LIGHTER_NATIVE_LIMIT_TIME_ALIGNMENT_LABEL` maps each P-fill label to
  source telemetry event time and the nearest historical Lighter account
  snapshot. It may mark active-order headroom as event-time aligned, but it must
  keep full native-limit pressure partial unless sendTx and REST pressure are
  explicitly observed at event time.
- `PHASE51N_MAKER_TAKER_ATTRIBUTION_RECOVERY_LABEL` records whether a filled
  row's maker/taker role was already complete, recovered from venue-native
  fill/trade evidence, partial, missing, or not applicable. It must not infer
  role from quote intent, post-only flags, strategy purpose, or fee schedules.

These Phase 5.1n labels are generated by
`tools/phase51n_lighter_native_limit_time_alignment.py` and
`tools/phase51n_maker_taker_attribution_recovery.py`. They remain `HOLD`,
non-live, nonfinancial evidence.

Phase 5.1o adds native role source inventory labels:

- `PHASE51O_NATIVE_ROLE_SOURCE_INVENTORY_LABEL` records whether each observed
  P_fill label has complete input maker/taker roles, exact canonical
  venue-native role evidence, unjoined source artifacts, incomplete canonical
  evidence, no fill, or missing source.
- `PHASE51O_NATIVE_ROLE_EVIDENCE` is emitted only when exact
  `canonical_group_id` venue-native role evidence exists from an allowed native
  source. It is the only 5.1o output intended for the 5.1n maker/taker recovery
  input.

These Phase 5.1o labels are generated by
`tools/phase51o_native_role_source_inventory.py`. They must not contain raw
order, client order, venue order, or trade identifiers; board-facing outputs
must use hashes, canonical group IDs, counts, and source classifications only.
They remain `HOLD`, non-live, nonfinancial evidence.

Phase 5.1p adds Lighter native-role canonical join labels:

- `PHASE51P_LIGHTER_NATIVE_ROLE_CANONICAL_JOIN_LABEL` records the attempted
  exact-hash join from canonical observed P_fill rows to quarantined Lighter
  native trade side identifiers, including status, hold reason, hash counts,
  matched native-trade hash counts, and effective maker/taker role counts.
- `PHASE51P_LIGHTER_NATIVE_ROLE_EVIDENCE` is emitted only when a Lighter
  canonical group has an exact hashed native side-ID match with complete
  maker/taker role counts. It is accepted by the Phase 5.1n maker/taker
  recovery gate as `LIGHTER_TRADES_JSON` evidence.

These Phase 5.1p labels are generated by
`tools/phase51p_lighter_native_role_canonical_join.py`. The tool may read raw
Lighter side identifiers inside the local quarantine process, but artifacts must
not contain raw order, client order, venue order, or trade identifiers. They
remain `HOLD`, non-live, nonfinancial evidence.

Phase 5.1q adds forward native-evidence capture labels:

- `V2_VENUE_NATIVE_ROLE_SAMPLE` is the normalized source event family for
  all-five venue explicit role fields: Lighter trade role, Hyperliquid
  `crossed`, Paradex `liquidity`, Aster order-update `m`, Extended `isTaker`,
  or another explicitly venue-native fill/trade field. It must not encode role
  from post-only intent, order purpose, fee schedule, or strategy assumptions.
- `V2_VENUE_NATIVE_LIMIT_PRESSURE` is the normalized source event family for
  event-time native limit pressure. For the current Phase 5.1 blockers, Lighter
  requires active/pending order headroom, sendTx headroom, REST/weighted request
  headroom, and event-time alignment before a row can be marked observed.
- `PHASE51Q_FORWARD_NATIVE_ROLE_CAPTURE_LABEL` records whether each canonical
  observed P_fill row was already complete, recovered from forward venue-native
  evidence, partial, missing, or not applicable.
- `PHASE51Q_FORWARD_NATIVE_ROLE_EVIDENCE` is emitted only for exact
  `canonical_group_id` role evidence from an allowed venue-native source. It is
  accepted by the Phase 5.1n maker/taker recovery gate.
- `PHASE51Q_NATIVE_LIMIT_PRESSURE_LABEL` records native-limit pressure status
  per canonical group. Non-Lighter rows are explicitly not applicable to the
  current Lighter-native-limit blocker; this does not waive future all-venue
  native-limit work.

These Phase 5.1q labels are generated by
`tools/phase51q_forward_native_evidence_capture.py`. Source rows and outputs
must not contain raw order, client-order, venue-order, fill, or trade IDs. They
remain `HOLD`, non-live, nonfinancial evidence and do not authorize model
training, EV admission, canary, capital, risk-limit changes, or live orders.

Phase 5.1s adds local native source-staging labels:

- `PHASE51S_LOCAL_SOURCE_LABEL` records the manifest source index, hashed local
  source path, source line, source-record hash, redacted source-record hash,
  join-key presence, complete Lighter native-limit field presence, and raw
  identifier strip count for every staged local source row.

These Phase 5.1s labels are generated by
`tools/phase51s_local_native_source_acquisition.py`. The tool rejects network
paths, `.env` files, symlinks, secret-shaped fields, unsafe true authorization
flags, and raw identifier leakage. Its `local_native_source.jsonl` output is
only a redacted input for Phase 5.1r and does not itself clear any model,
execution, or evidence blocker.

Phase 5.1r adds forward native source-acquisition labels:

- `PHASE51R_NATIVE_ROLE_SOURCE` is the redacted source row emitted from a local
  read-only venue-native snapshot. It carries `canonical_group_id`, `venue_id`,
  maker/taker role counts, an allowed venue-native attribution source, and a
  source-record hash.
- `PHASE51R_NATIVE_LIMIT_SOURCE` is the redacted Lighter native-limit source row
  emitted for canonical groups with event-time active-order, sendTx, and
  REST/weighted-request context.
- `PHASE51R_SOURCE_ACQUISITION_LABEL` records the source-acquisition status for
  each inspected local source row without emitting raw venue identifiers. It
  also records `canonical_group_link_source`, which is
  `SOURCE_ROW_CANONICAL_GROUP`, `SOURCE_ROW_ORDER_KEY`,
  `SOURCE_LINK_SIDECAR`, or `NO_CANONICAL_LINK`.

These Phase 5.1r labels are generated by
`tools/phase51r_forward_native_source_acquisition.py`. Raw local input snapshots
may contain venue identifiers, but Phase 5.1r outputs must not contain raw
order, client-order, venue-order, fill, or trade IDs. The outputs are designed
to feed Phase 5.1q and remain `HOLD`, non-live, nonfinancial evidence.
Optional Phase 5.1r source-link sidecars may map redacted source-record hashes
to observed `canonical_group_id` or `order_key`; those sidecars must validate
against observed P-fill labels and cannot infer venue-native fields.

M6 risk/system precondition fields are emitted on candidate EV records:

- `pair_conditioned_flag`
- `fast_hedge_allowed`
- `fast_hedge_serialization_state`
- `residual_state_required`
- `residual_state_status`
- `action_owner`
- `double_action_prevention_state`

The current non-live shadow scaffold sets these to no-action/no-fill states:
there is no order intent, no fast hedge, no residual inventory, and no active
inventory action owner. Future order/fill/hedge emitters must replace these
placeholders with event-sourced ownership and residual-state records before
any non-shadow execution path can be reviewed.

Event-family-specific required fields can be tightened further once emitters are
producing stable artifacts for order lifecycle, fill, hedge, inventory, and
balance events.

## Determinism

Phase 5.1 non-live runs should provide a stable `run_id` and input telemetry
snapshot. The shadow harness derives replay timestamps from the run id and input
hash unless `--replay-timestamp-ns` is provided, and writes a root
`manifest.json` covering the run artifacts.

## Validation

```bash
python3 tools/check_telemetry_contract.py path/to/telemetry.jsonl
python3 tools/check_telemetry_contract.py path/to/run_directory/
```

Existing v1 telemetry remains valid and should continue to emit
`schema_version: 1` until a producer intentionally migrates to v2.
